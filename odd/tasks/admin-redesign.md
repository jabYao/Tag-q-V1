# Admin redesign — Agenda operativa

Objective: redesign every Tag q admin screen and add a server-rendered dashboard as the admin home, in the chosen Agenda operativa composition.
Branch: current branch. Work is committed on the current branch by explicit user instruction; push remains unauthorized.
Delivery: local commits only; not pushed. Test runner: `php artisan test` against PostgreSQL `tagq_testing`; asset check: `npm run build`.

## Specs

- **S1 — Scope.** Redesign all admin areas: dashboard, products, orders, collections, and users/team. The storefront is out of scope and must not be touched.
- **S2 — Dashboard.** New admin home at `/admin` (`admin.dashboard`) with current-month sales, orders by status, low-stock products, and active users. Server-rendered Blade + Eloquent using existing admin routes/controllers; no new admin JSON API.
- **S3 — Roles.** Admin and Empleado use the full admin shell and dashboard. Collections, Users/Team, and the dashboard team data remain Admin-only; existing controller restrictions stay intact. Guests and customers stay out.
- **S4 — Shell.** Replace the generic `layouts.app` admin shell with a dedicated admin layout. Keep existing admin route names and the `admin.productos.*` alias; add only `admin.dashboard`. The storefront continues to link to `admin.products.index`.
- **S5 — Composition.** Use the locked Agenda operativa: 232px navy rail, HOY header, current-month sales with seven honest day bars, five-state order rail, eight-row agenda, 300px operational side rail, flat paper/white surfaces, hairline rules, Bebas/Outfit/Inter/Jost, hang tag + status stamp + lume rail. Refuse the generic SaaS dashboard, the old CRUD shell, marketing hero, gradients, and nested cards.
- **S6 — Order truth.** Preserve exact order status values and Spanish labels: `pendiente_de_pago` = Pendiente de pago, `pagado` = Pagado, `en_preparacion` = En preparación, `enviado` = Enviado, `entregado` = Entregado, `cancelado` = Cancelado, `reembolsado` = Reembolsado. One-step transitions only, Wompi remains authoritative, no overselling.
- **S7 — Sales definition.** Current-month sales = sum of `Order.total` for orders created in the current month with status `pagado`, `en_preparacion`, `enviado`, or `entregado`. Pending, canceled, and refunded are excluded. Verify in tests.
- **S8 — Low stock.** Use `stock <= 3` for active products as the working alert cutoff, visibly labeled provisional because the business has not confirmed the threshold. Inactive products are excluded from the alert list.
- **S9 — Preserve function.** Products CRUD with Admin-only create/delete and Admin-only price/stock/is_active edits; Employees may edit only allowed fields. Orders list/detail with filters, status advance, cancel, and refund. Collections Admin CRUD. Users Admin CRUD plus active toggle. Invoice/order links that exist today must keep working.
- **S10 — Testing.** Every new feature ships with its test; update existing admin/auth tests for the new shell and login destination. `php artisan test` must pass complete before delivery. No `--no-verify` or skipped tests.
- **S11 — Responsive.** The admin must compose at 1440×900 and at 390px: rail collapses to a horizontal header, the side rail stacks, tables scroll horizontally, forms go one column, focus/disabled/error/empty states remain legible.
- **S12 — Finish.** Capture 1440×900 and 390 screenshots, run the accessible/contrast/checklist finish review, document the built visual world in DESIGN.md, and record raster provenance if screenshots ship. Keep all changes uncommitted.
- **S13 — Delegation.** Use the design skill and its finish reviewer/documenter. Delegate independent screen units after the shared shell exists; the parent owns the shell, dashboard, CSS, and final verification.
